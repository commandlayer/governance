# RFC Process

## Purpose

Define the mandatory process for proposing and accepting governance, protocol, and cross-repository coordination changes.

## RFC Lifecycle

1. **Draft**: proposal submitted with problem statement, scope, and impact analysis.
2. **Review**: maintainers and affected repository owners evaluate technical and governance impact.
3. **Decision**: proposal is accepted, rejected, or withdrawn with rationale.
4. **Implementation Alignment**: accepted changes propagate to policy artifacts and repository plans.
5. **Closure**: decision recorded in `DECISION_LOG/` and linked to release/audit artifacts as required.

## Required RFC Sections

- context and problem statement,
- proposed change,
- repository impact map,
- release sequencing impact,
- versioning and compatibility impact,
- security implications,
- alternatives considered,
- decision outcome.

## Normative Requirement

Any change affecting release policy, versioning semantics, compatibility interpretation, or security governance MUST follow this RFC process.
